   132→PART I — PRODUCT FOUNDATION
   133→BAB 1 — Executive Summary
   134→Why
   135→Sebelum menulis satu baris kode pun, sebuah startup butuh satu dokumen yang menjawab
   136→pertanyaan paling dasar: “Sebenarnya kita sedang membangun apa, dan kenapa itu penting?”
   137→Banyak startup gagal bukan karena tekniknya buruk, tapi karena tim (termasuk founder sendiri)
   138→tidak punya pemahaman yang sama tentang apa yang sedang dibangun. Executive Summary
   139→adalah “kompas” — dokumen pertama yang dibaca siapa pun (investor, developer baru, cofounder) untuk memahami keseluruhan proyek dalam waktu singkat.
   140→What
   141→• Nama Produk: Project Alpha
   142→• Tagline: Trade Better. Think Better. Become Better.
   143→• Kategori Produk: AI Trading Coach — bukan trading journal biasa, bukan signal provider,
   144→bukan robot trading.
   145→Value Proposition Inti: Project Alpha membantu trader yang sudah bisa membaca chart dan
   146→sudah punya strategi sendiri untuk naik level melalui: pencatatan trading terstruktur (AI
   147→Journal), analisis screenshot chart oleh AI, review otomatis setiap trade, deteksi pola perilaku
   148→trading (disiplin, emosi, konsistensi), dan coaching berbasis percakapan yang “mengenal”
   149→perjalanan trader tersebut dari waktu ke waktu.
   150→Diferensiasi Utama: Kompetitor kebanyakan menjual “sinyal” atau “otomatisasi”. Project Alpha
   151→menjual kesadaran diri (self-awareness) trader — produk ini menang bukan karena akurasi
   152→prediksi pasar, tapi karena kualitas refleksi yang dihasilkan.

  1135→BAB 20 — Security & Data Privacy Architecture
  1136→Why
  1137→Project Alpha menyimpan data psikologis dan perilaku trader (Bab 14, 15) — data yang kalau
  1138→bocor dampaknya bukan cuma finansial tapi personal. Alpha Promise (Bab 2) hanya bernilai
  1139→kalau trader percaya datanya aman.
  1140→What
  1141→2.1 Prinsip Inti — Defense-in-Depth: RLS di database tetap dibutuhkan meski Frontend tidak
  1142→pernah panggil Supabase langsung (Bab 19) — RLS adalah lapis otorisasi kedua yang menyala
  1143→kalau lapis pertama (application-level) gagal karena bug atau komponen baru yang lupa
  1144→mengecek trader_id.
  1145→2.2 Empat Domain Keamanan: Authentication (CP-05), Authorization, Data Protection, Input
  1146→Integrity.
  1147→2.3 Authentication (CP-05): Supabase Auth, JWT access token pendek + refresh token
  1148→rotasi (mengikuti mekanisme resmi Supabase Auth SSR/session helper — token tidak pernah
  1149→terekspos ke JavaScript client secara langsung, implementasi detail tidak dikunci di level
  1150→arsitektur).
  1151→2.4 Authorization — Dua Lapis: - Lapis 1 (Application-Level): trader_id tidak pernah
  1152→diterima dari parameter caller — Repository/Command Handler wajib mengambil trader_id
  1153→dari authentication context (session), bukan dari argumen bebas pemanggil. - Lapis 2
  1154→(Database-Level RLS): setiap tabel yang di-scope per trader wajib punya RLS policy
  1155→trader_id = auth.uid().
  1156→2.5 Service Role Key: hanya dipegang MemoryWriteService/MemoryReadService dan
  1157→Repository infra tertentu. LLM Gateway TIDAK memegang service role — kredensialnya
  1158→terpisah (OPENAI_KEY), karena ia tidak berinteraksi dengan Supabase sama sekali.
  1159→2.6 Data Protection: TLS wajib di seluruh koneksi; encryption at rest bawaan Supabase/PostgreSQL;
  1160→screenshot (CP-06) lewat signed URL berumur pendek (15 menit), bukan public bucket; Memory
  1161→L0/L1/L2 diklasifikasikan sensitive behavioral data, akses hanya lewat kontrak Memory.
  1162→2.7 Input Integrity — Untrusted User Content: seluruh konten bebas dari trader (chat, catatan
  1163→trade) diperlakukan sebagai untrusted input, bukan sekadar disaring kalau mencurigakan.
  1164→Konten trader dirakit ke prompt selalu sebagai data yang di-delimit eksplisit, tidak pernah
  1165→disisipkan sebagai instruksi sistem. Deteksi pola mencurigakan tetap ada sebagai lapis
  1166→logging/flagging tambahan, bukan pertahanan utama.
  1167→2.8 Rate Limiting: per-trader, melengkapi rate limit agregat LLM Gateway (Bab 13) —
  1168→pertahanan tambahan terhadap brute-force prompt injection.
  1169→2.9 Data Retention & Right to Erasure: soft-delete 30 hari lalu hard-delete terjadwal
  1170→(melanjutkan Bab 17). Retensi audit log terpisah: event_log 90 hari lalu diarsipkan;
  1171→dead_letter_events 90 hari setelah resolved lalu dihapus.
  1172→2.10 Secret Management: seluruh secret hanya di environment variable; tidak pernah commit
  1173→Git; tidak pernah dikirim ke Client Component; rotasi key tanpa perubahan kode aplikasi; AI
  1174→coding assistant tidak boleh menulis secret secara hardcoded dalam kondisi apa pun.
  1175→Technical Decisions (ringkas): dua lapis otorisasi wajib (defense-in-depth); service role key
  1176→least-privilege, terpisah dari OPENAI_KEY; signed URL untuk aset privat; input sanitizer sebagai
  1177→struktur prompt, bukan filter kata kunci; rate limit per-trader; retensi audit log terpisah dari
  1178→retensi data trader.

  1248→BAB 22 — Coding Standards
  1249→Why
  1250→Peta folder saja tidak mencegah kode melanggar Service Boundary secara isi. Project Alpha
  1251→dikerjakan lintas AI coding assistant tanpa memori bersama — konvensi harus eksplisit dan
  1252→sebisa mungkin ditegakkan tooling.
  1253→What
  1254→• 2.1 Naming Conventions: PascalCase untuk file Domain/Infrastructure/Handler;
  1255→EventName.vN.ts untuk event; kebab-case route; snake_case DB; akhiran Repository
  1256→untuk interface.
  1257→• 2.2 TypeScript Standards: strict: true wajib; any dilarang di domain/commands/queries;
  1258→explicit return type wajib di fungsi export; interface untuk kontrak implementable, type
  1259→untuk bentuk data.
  1260→• 2.3 Import Rules — ditegakkan lewat ESLint boundary rule: lib/domain/** tidak boleh
  1261→import lib/infrastructure/** (kecuali interfaces/**) atau SDK eksternal; app/**
  1262→tidak boleh import infra langsung.
  1263→• 2.4 Error Handling Standard — taksonomi exception: ValidationError (400),
  1264→UnauthorizedError (401), ForbiddenError (403), NotFoundError (404 — sengaja
  1265→disatukan dengan kasus akses ditolak RLS agar tidak membocorkan keberadaan data
  1266→trader lain), InsufficientDataError (422), GuardrailViolationError (internal,
  1267→fallback template), ExternalServiceError (503).
  1268→• 2.5 Event Contract Standard: setiap event wajib field event_type (versi eksplisit),
  1269→correlation_id, trader_id, occurred_at, payload.
  1270→• 2.6 Comment & Documentation Standard: JSDoc fungsi export wajib menyebut
  1271→referensi Bab.
  1272→• 2.7 Secret & Config Usage Standard: akses env hanya lewat lib/infrastructure/config/env.ts;
  1273→ESLint custom rule menolak pola literal mirip API key; build gagal kalau env wajib kosong.
  1274→• 2.8 Code Review Checklist: trader_id dari auth context; file sesuai Ownership; event
  1275→baru versi eksplisit; pattern/template baru mulai status Experimental; tidak ada exception
  1276→generik.
  1277→RECOMMENDATION — Standar ini jadi gerbang wajib sebelum kode di-merge,
  1278→terlepas siapa penulisnya.

  1311→BAB 24 — Observability & Monitoring Architecture
  1312→Why
  1313→Sistem event-driven asinkron (Bab 13) berarti kegagalan komponen backend bisa terjadi
  1314→berhari-hari tanpa disadari, karena trader tetap menerima “200 OK” tanpa menunggu rantai
  1315→penuh selesai.
  1316→What
  1317→• 2.1 Tiga Pilar: Logging (event_log, Admin Log), Metrics (agregat event), Tracing
  1318→(correlation_id).
  1319→• 2.2 Correlation ID sebagai Trace: query tunggal SELECT * FROM event_log WHERE
  1320→correlation_id = X menghasilkan trace lengkap lintas komponen — tidak perlu tooling
  1321→tracing terpisah di skala MVP.
  1322→• 2.3 Golden Signals: Sinyal Kritis (rate penolakan Guardrail naik tajam, event masuk DLQ,
  1323→pola akses RLS tidak wajar) → alert real-time; Sinyal Penting (distribusi confidence score,
  1324→rate InsufficientDataError, latency LLM Gateway) → dashboard harian; Sinyal Informatif →
  1325→tersedia bila dibutuhkan.
  1326→• 2.4 Guardrail Violation Rate: metrik produk paling penting di seluruh sistem — rate
  1327→naik >3x baseline → alert <15 menit.
  1328→• 2.5 DLQ sebagai Sinyal Kesehatan: alert otomatis saat event pertama masuk DLQ —
  1329→terpisah dari retensi 90 hari (Bab 20), yang hanya soal berapa lama bukti disimpan.
  1330→• 2.6 Dashboard Kalibrasi: alat internal terpisah total dari CF-02 milik trader,
  1331→menampilkan distribusi confidence_score per pattern.
  1332→• 2.7 Privasi dalam Observability: log/metrik tidak boleh memuat isi percakapan mentah
  1333→— hanya event_type, correlation_id, trader_id, timestamp, metadata teknis.
  1334→RECOMMENDATION — Observability ini wajib berjalan sejak MVP (tidak boleh
  1335→ditunda Fast-Follow) karena berhubungan langsung dengan Alpha Promise.
